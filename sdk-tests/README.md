The S3 smoke profile uses `request_checksum_calculation="when_required"` so ordinary multipart upload, versioning, and presigned part workflows remain independently testable. This is an explicit botocore configuration optout from its default additional-checksum behavior. Passing that profile does not establish parity with default boto3 multipart requests.

`test_s3_direct_put_native_checksums_and_rejection` uses the current native `when_supported` profile. It verifies CRC32, CRC32C, CRC64NVME, SHA1, SHA256, and MD5 on direct PUT with independent digest vectors, persisted retrieval identities, and rejection without overwrite. The native default direct PUT CRC32 path is also tested.

`test_s3_native_default_multipart_checksum_boundary` requires explicit-checksum multipart initiation and default boto3 part upload to return S3 `501 NotImplemented`, without creating an upload or storing a part. Current botocore default initiation carries no checksum and succeeds; its default part upload adds CRC32 and is rejected. Completion manifests containing checksum fields are also rejected without consuming existing parts. Additional-checksum multipart, explicit checksum selection on copy, SHA512/XXHASH algorithms, and `aws-chunked` checksum trailer requests remain unsupported. An HTTP checksum trailer that reaches the body collector is rejected as an incomplete body before dispatch; its spool is removed.

Direct PUT checksum identities use Base64 network-byte-order values and `FULL_OBJECT`. GET and HEAD return them when `ChecksumMode="ENABLED"` is requested. Range responses omit whole-object checksums. Direct replacement clears omitted checksum identities; byte-preserving copy retains them. HTTP Cache-Control, Content-Encoding, Content-Language, and Content-Disposition survive restart, COPY, and plain multipart initiation/completion; REPLACE and fresh PUT reset omitted properties.

The native contract is described in the [PutObject API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html), [CreateMultipartUpload API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CreateMultipartUpload.html), [UploadPart API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_UploadPart.html), and [CompleteMultipartUpload API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html).

Tagging and ACL request checksums are transactional checksums of their request body: supported algorithms are validated before metadata mutation, and they do not replace the stored object checksum identity. S3 full GET/copy and selected byte ranges have a named 64 MiB materialization bound; larger full requests return `501 NotImplemented` before payload reads. Large streamed PUT, current/historical HEAD, and small current/historical ranges remain supported. Azure likewise bounds full reads, snapshots, metadata writes, append/page mutations, and PageBlob extent at 64 MiB with `501 FeatureNotSupported`; lease/WORM updates and all HEAD selectors use metadata reads. These limits qualify the implemented subset rather than native maximum object sizes.

Azure current, snapshot and version GET/HEAD implement ETag lists, date predicates at HTTP-date precision, active-lease predicates, and modern Azure combined-read condition precedence. Unimplemented `x-ms-if-tags` read predicates return `501 FeatureNotSupported`. Date and tag predicates on mutations, including snapshot creation, also return that native error before any state change; their accepted subset remains partial.
